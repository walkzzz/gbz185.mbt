## 三、深边界用例结果

### 1. 信封编码（11 例）

| 输入 | 结果 |
|---|---|
| seq=0 / -5 / 1.5 / 2^31 | 全部拒绝："seq 必须是 1..2147483647 的整数（int32 演示范围）" |
| seq=i32max | 正常编码 |
| timestamp=-1 | 拒绝："timestamp 必须是 0..2147483647 的整数（int32 演示范围）" |
| timestamp=0 | 正常编码 |
| payload=`[]` / `"str"` / `null` | 均按 JSON 原样嵌入（数组、字符串、null 合法 JSON） |
| payload 嵌套 + 中文 + 转义换行 | 正确序列化 `{"t":"你好\n世界","n":1.5}` |
| payload 非法 JSON | `invalid payload JSON` |
| sender/recipient 为空 | `sender / recipient URN 不能为空` |

### 2. 信封校验（17 例，仅 3 例通过）

- 通过：默认合法信封、额外字段（前向兼容）、带空白/换行格式的等价 JSON。
- 拒绝：protocol=rpc、protocol=AIP（大小写敏感）、version="1.0"、version=数字 1、缺 version、seq 为字符串、seq=0、seq 负数、kind=TASK_REQUEST、kind 带尾空格、缺 payload、sender 空、空对象、顶层数组。
- 结论：结构与取值语义（非空 URN、seq>0、timestamp≥0）双重校验，判词稳定。

### 3. 信封元数据（8 例）

- kind 未知、缺 kind、version 数字型、坏 JSON → `invalid AIP envelope` / `invalid JSON`。
- 额外字段、嵌套 payload → 正常。
- **seq=0 被接受**，返回 `message_id: "urn:agent:b#0"`（与校验卡拒绝 seq=0 的口径不一致，见 R1）。

### 4. 序号推进（9 例）

1→2 正常；0、-5、1.5、2147483647、2^31、2^53、非数字、空值全部拒绝，文案含"保证 +1 不回绕"。范围边界处理干净，不再出现回绕或精度丢失展示。

### 5. 完整流程（9 例）

3 对端正常；重复对端自动去重（`p1, p1` → peers `["urn:agent:p1"]`）；50 对端正常返回 50 个 URN；空/仅空格对端报 `at least one peer URN required`；node 为空报 `node URN required`；payload 坏 JSON 报错；payload 为数组/字符串可接受。
遗留：`bad urn` 这类非法 peer、node `x y` 仍被接受（见 R2）。

### 6. 能力匹配（8 例）

子集 → covered true；空需求 → covered true；空具备 → covered false + 缺失清单；重复需求去重；大小写敏感（`SKILL:demo` 不匹配）；不支持通配 `skill:*`；多缺失按需求顺序输出；逗号两侧空格被裁剪。

### 7. 发现过滤（7 例）

空 filter → 返回全部可见节点；全隐藏 → 0；10 节点按能力筛出 5 个；缺 acs / 非对象元素 → `invalid node JSON`；能力大小写敏感 → 0；重复 URN 节点两条都返回（未去重，见 R3 相关）。
开关复测：取消"仅返回 discoverable"→ 2 条（含隐藏节点 C），勾选 → 1 条，开关生效。

### 8. AIC 身份码（13 例）

合法：`1.2`、`1.2.156.185.2.1`、`1.2.156.185.2.1.42.99`、`01.02`（前导零被接受）、`1.2.156.185.2.1.999999999`（超大段被接受）。
非法：单段 `1`、`1..2`、`a.b`、`-1.2`、`1.2.-3`、全角 `１.２`、`.1.2`、`1.2.`（末尾空段）。
边界口径：前导零与段值上限未定义，建议 README 明确。

### 9. 路由解析（7 例）

默认 fanout 2 成员；组名不一致 → `unknown group`；recipient 空 → `unroutable recipient`；成员空 → `empty group`；成员重复 → 去重后 1 个（fanout）；单成员正常。

### 10. 工具描述（11 例）

schema 为数组/字符串/null/数字 → `invalid descriptor (name/description empty or schema not object)`；schema 缺 properties → 合法；name 含空格、全大写、64/65 字符、description 1024/1025 字符 → **全部合法**（见 R4）。

## 四、本轮发现（均为低级别或提示）

### R1（低）元数据卡接受 seq=0，与校验卡口径不一致

- 实测：`seq:0` 信封在校验卡判"非法"，但元数据卡解析成功并给出 `message_id "urn:agent:b#0"`。
- 影响：同一字段两处判定不一致，读者难以判断 0 是否合法序号。
- 建议：`aip_envelope_meta` 复用与 `aip_validate` 相同的序号/URN 取值校验，或在卡片文案标注"仅解析字段，不做取值校验"。

### R2（低）URN 仅校验非空，不校验格式

- 实测通过：sender `not-a-urn`、`URN:AGENT:Demo`、300 字符超长 URN、含空格 `urn:agent:a b`；peer `bad urn`；node `x y`（message_id 变成 `x y#1`）。
- 影响：协议演示里"URN"实际等价任意非空字符串，与 AIC 卡的严格校验形成对比。
- 建议：至少校验 `urn:` 前缀与字符集（RFC 8141 简化版），并在卡片注明长度上限。

### R3（低）扇出计数不去重，与路由卡口径不一致

- 实测：成员 `m1, m1, m2` → 扇出卡 `fanout_count: 3`；同类输入在路由卡返回去重成员 `["urn:agent:m1"]`。
- 影响：两卡对"重复成员"给出不同数量，容易被理解为可重复投递。
- 建议：扇出计数前按 URN 去重，或输出 `unique_count` 与 `raw_count` 两项。

### R4（低）工具描述缺 MCP 命名规范校验

- 实测通过：name 含空格 `net fetch`、全大写 `NET_FETCH`、64/65 字符、description 1024/1025 字符。
- 影响：MCP 客户端普遍要求 `[A-Za-z0-9_-]{1,64}` 的工具名，当前输出可能被真实宿主拒绝；同项目 SKILL.md 校验对 name 有 64 字符上限，口径不统一。
- 建议：增加 name 字符集与长度校验，description 长度上限。

### R5（提示）移动菜单浮层在截图管线中不可见

- 现象：菜单展开后，`.nav` 计算样式为 `display:flex; position:absolute; background:#fff; opacity:1`，924×304，z-index 45，命中测试在整个面板区域均返回对应链接，点击可跳转并自动关闭；但页面截图（含 `.nav` 元素裁剪图）拍到的是其下方的 hero 内容。
- 判断：功能层完好（可点、可达、aria-expanded 正确），仅截图未捕获该绝对定位浮层，疑为截图合成/捕获时序问题，**建议真机目视确认一次**。
- 备注：本轮尝试用桌面截屏交叉验证时，虚拟桌面因 Windows 账户空密码被系统拒绝（Win32 1327 / LOGON32_LOGON_NETWORK），未接管主桌面；该限制与页面本身无关。

### R6（提示）int32 上限与 i64 宣传并存，已由文案说明

卡片已明确"数字参数为 int32 演示范围（i64 语义由库内 verify 证明覆盖）"，属可接受设计；建议性能/质量区同步一句同样的限定，避免只读数字区的读者误解。

### R7（提示）性能

index.html 35.1KB、style 16.6KB、app 11.5KB、playground 352KB；本轮 DCL 630ms / load 643ms（上一轮同环境 217ms，波动较大，首要成本仍是 352KB 单文件）。建议 minify/gzip 或拆分模块。
